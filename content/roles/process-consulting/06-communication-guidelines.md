# Communication Guidelines

Two layers here. GPC's baseline rules for which channel carries what, and
how Grant himself actually writes to clients in email, pulled from real
sent messages the same way the Grant Way playbook pulls patterns from real
call transcripts. The second layer is a starting sample, not a finished
study. Add to it as more threads come in.

## Which channel, for what

GPC runs four communication tools, each with a job. Mixing them up is how
requirements, deadlines, and decisions go missing.

| Tool | Job |
|---|---|
| Slack | Internal hub: questions, updates, team announcements, tools and wins. Client communication only when that client has an active shared Slack channel. |
| ClickUp | Client work: tasks, project updates, requirements, blockers, deadlines, deliverable status. Every engaged client gets a ClickUp chat channel at the folder level. |
| HubSpot | Sales activity: calls, meetings, sales emails, deal notes, pipeline updates. |
| Email | The external gap: a client who doesn't use Slack, a formal or long-form message, an external stakeholder outside the normal tools. |

<Callout>If a conversation changes the work, creates a requirement, or affects a deal, it gets captured in the tool that owns that kind of record, not left to live only in the channel it happened in.</Callout>

## The 1-3-1 method for problem resolution

When something breaks, or a requirement wasn't fully known at build time,
this is the shape of the response: one problem, three solutions, one
recommendation.

1. **One problem.** State it in one or two sentences: name the thing
   affected and what went wrong. Don't propose a solution yet.
2. **Three solutions.** Stretch past the first answer that comes to mind.
3. **One recommendation.** Weigh the three, name the one you'd move forward
   with, and say why.

If more than one problem surfaced, run the method once per problem rather
than blending them into one response.

For an automation error specifically: lead every response, proactive or
reactive, with one plain sentence naming what the automation does before
anything else. Acknowledge the client's frustration directly on a
financial-impact error.

<Callout>Never blame the client's data before investigating. If a fix will take more than ten minutes, create a ClickUp task and tag the Operations Manager rather than going quiet while you work it.</Callout>

## How Grant actually writes to clients

Everything below is observed from real sent email to Rush Enterprises,
Coffee & Clothes, and Cooper Erving & Savage, not a style guide someone
wrote from theory. Study the pattern, not the exact words.

| Pattern | What it looks like |
|---|---|
| First name, no formal salutation | "Hey Jason," "Hey RJ," "Hey Amber," even to a senior contact he's never met. Sign-off is "Grant," never "Regards" or "Sincerely." |
| The first sentence answers the reason for the email | No warm-up. A scheduling reply opens with which time works; a contract update opens with what changed. |
| Short paragraphs, one idea each | Even the longest sampled emails run three or four short paragraphs, never a wall of text. |
| Scheduling options as a bulleted list, time zone stated every time | Not folded into a sentence. |
| Real internal context shared plainly, not deflected | Told a client sponsor directly that a launch date moved because of a shift in AI market sentiment that week, and named whose read on it he trusted. |
| One line acknowledges the other person's point first | "Heard on lead time, we're in lock step!" comes before the substance of the reply. |
| A confirmation can be one line | "Confirmed on our end. Thank you!" is the whole email. |
| Direct access offered when responsiveness matters | A cell number and an availability window ("I'll be around until about 9PM EST") on a time-sensitive request. |
| Sign-off rotates and stays warm | "Thank you kindly and hope you had a great weekend," "Have a great week ahead," "Be well." Never a generic "Best regards." |

Scheduling example, time zone stated every time:

```
Do any of these times (CDT) work?

- tomorrow (Sep 15): 12:30-1:30 pm, 4:00-5:00 pm
- Wed Sep 16: 1:00-2:00 pm
- Thu Sep 17: 12:30-1:30 pm
```

The signature block itself never varies:

```
Best,
Grant Hushek
CEO, Grantbot & GPC

Sent via Superhuman
```

One honest exception worth naming: GPC's own authored documents ban the em
dash outright (see `gpc-skills/skills/gpc-brand-docs/references/voice-and-slop.md`).
Grant's actual informal client email doesn't always follow that: one sampled
email opens "Hey Amber — Friday 9/18 at 11:00am ET works." This module
describes what he does, not a rule to import elsewhere. The em dash ban
stays in force for anything GPC drafts as a formal deliverable.
